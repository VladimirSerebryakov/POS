# ПОС – преподавательская оценка студентов

Консольное приложение на Go для второго домашнего задания по конструированию ПО. ПОС - шуточное «СОП наоборот»: преподаватель оценивает студентов по критериям «Ходил на пары», «Не ныл» и «Задавал вопросы».

Программа проверяет оценки, считает итог и сохраняет отчёт. Используются DDD, архитектура Ports and Adapters и паттерны GoF: Builder, Facade и Strategy.

## Как запустить

Нужен Go версии `1.27.0`.

Из корня проекта:

```bash
go run ./cmd/pos
```

Сначала нужно собрать рубрикатор - общий список критериев: добавить хотя бы один и подтвердить сборку. Затем откроется меню студентов, критериев, оценок, итогов и экспорта.

В меню выбирается номер действия. ID студентов и критериев назначаются автоматически. Пункт `0` завершает работу. После ошибки можно продолжить ввод.

## Пример работы

1. Добавить два критерия: «Ходил на пары» с максимумом 10 и весом 3, «Задавал вопросы» с максимумом 5 и весом 2. Завершить сборку рубрикатора.
2. Добавить студента «Иванов Иван Иванович», группа «БПИ-251».
3. В пункте `7` выставить ему 8 баллов за посещение и 5 за вопросы по ID студента и критериев.
4. В пункте `10` посмотреть оценки. В пункте `11` получить итог: `8.80`.
5. В пункте `13` выбрать `json` или `csv`. Отчёт сохранится в `reports/report.json` или `reports/report.csv`.
6. При необходимости исправить оценку через пункт `8` или отменить через пункт `9`. Следующий расчёт и экспорт учтут изменения.

Также доступны список студентов, изменение рубрикатора и итоги всех студентов.

## Правила и расчёт итога

У студента есть ID, непустые ФИО и группа. Одинаковые ФИО допустимы: студенты различаются по ID.

У критерия есть непустое название, положительный целочисленный максимум и целочисленный вес от 1 до 5. Вес определяет вклад критерия в итог; сумма весов произвольная.

Оценка - целое число от нуля до максимума существующего критерия. Для пары «студент - критерий» хранится одна оценка. Повторное выставление отклоняется; исправление выполняется отдельно.

При просмотре ноль отличается от «не выставлено». При расчёте пропуск считается нулём, но вес критерия учитывается.

Формула приводит результат к шкале от 0 до 10:

```text
итог = 10 × сумма(вес × балл / максимум) / сумма весов
```

Критерий можно менять или удалять, если по нему нет оценок, включая нулевые. Последний критерий удалить нельзя.

## Хранение данных и отчёта

В приложении один список студентов и один общий рубрикатор. Все данные хранятся в памяти.

Отчёт содержит ФИО всех студентов и их итоги. Пример JSON:

```json
[
  {"student": "Иванов Иван Иванович", "total": 8.8}
]
```

Тот же отчёт в CSV:

```csv
student,total
Иванов Иван Иванович,8.80
```

Пользователь выбирает только формат. Папка `reports/` создаётся автоматически в рабочем каталоге, после сохранения программа показывает полный путь.

## DDD

Студент, критерий, рубрикатор, оценка и итог – единый язык предметной области (Ubiquitous Language).

| Понятие DDD | Что ему соответствует в проекте | Почему |
| --- | --- | --- |
| Entity – сущность с идентичностью | `Student`, `Criterion` | Объекты различаются по ID, даже если их имена совпадают |
| Entity | `Evaluation` | Определяется парой ID студента и критерия. Исправление меняет только балл |
| Value Object – объект-значение | `Weight` | Веса с одинаковым значением равнозначны. Допустимы значения 1–5 |
| Repository – интерфейс доступа к сохранённым данным | `StudentRepository`, `RubricRepository`, `EvaluationRepository` | Сценарии могут загружать и сохранять данные, не зная, как устроено хранилище |
| Domain Service – доменное правило, затрагивающее несколько объектов | `Calculator`, `EvaluationService`, `RubricService` | Расчёт зависит от рубрикатора и оценок, а изменение критерия требует проверить оценки всех студентов |

Конструктор `Evaluation` проверяет диапазон балла, а `EvaluationService` - наличие критерия в рубрикаторе и отсутствие повторной оценки. Поля моделей закрыты, коллекции возвращаются копиями. Правила действуют и при вызове сценариев без консоли.

Рубрикатор с критериями образует агрегат и сохраняется целиком.

## Архитектура Ports and Adapters

В центре приложения - правила оценивания. Консоль, хранение и экспорт подключаются снаружи. Порт - Go-интерфейс нужных операций, адаптер - его реализация или способ взаимодействия с приложением.

| Папка | Что в ней находится |
| --- | --- |
| [internal/domain](internal/domain) | Студент, критерий, вес, оценка, рубрикатор и его Builder. Здесь проверяются ограничения самих объектов |
| [internal/domain/service](internal/domain/service) | Правила выставления оценок, расчёт итога и изменение критериев с учётом оценок. Это тоже часть доменного слоя |
| [internal/application](internal/application) | Прикладные сценарии и порты. Например, загрузить студента, вызвать доменную операцию и сохранить оценку |
| [internal/adapters/cli](internal/adapters/cli) | Консольное меню, чтение ввода, вывод сообщений и работа с файлами отчётов |
| [internal/adapters/memory](internal/adapters/memory) | Реализации репозиториев, которые хранят данные в памяти |
| [internal/adapters/report](internal/adapters/report) | Запись отчёта в JSON и CSV |
| [internal/adapters/formatting](internal/adapters/formatting) | Общее округление итогов для консоли и отчётов |
| [cmd/pos](cmd/pos) | Запуск программы и сборка зависимостей через ручной DI-контейнер |

Основные зависимости направлены внутрь:

```text
cli ──────→ application ──────→ domain/service ──────→ domain
memory ───→ application, domain
report ───→ application
```

Прикладной слой также использует доменные объекты напрямую.

При выставлении оценки консоль передаёт ID и балл прикладному сценарию. Тот загружает студента, рубрикатор и оценки, вызывает доменный сервис и сохраняет результат.

Интерфейсы хранилищ и экспортёра находятся в [application/ports.go](internal/application/ports.go). Реализации в `adapters` зависят от этих интерфейсов.

## Паттерны GoF

| Группа | Паттерн | Где используется | Какую задачу решает |
| --- | --- | --- | --- |
| Порождающий | **Builder** | [RubricBuilder](internal/domain/rubric_builder.go) | Собирает критерии по одному, проверяет их корректность и уникальность ID. `Build()` отклоняет пустой набор |
| Структурный | **Facade** | [application.Service](internal/application/service.go) и его методы сценариев | Объединяет сценарии для консоли: загружает данные, вызывает доменные правила и сохраняет результат |
| Поведенческий | **Strategy** | Порт `ReportExporter` и [экспортёры JSON/CSV](internal/adapters/report) | Позволяет выгружать один и тот же отчёт разными способами, сохраняя общий расчёт итогов |

Стратегия экспорта выбирается по формату пользователя: обе реализации получают одинаковые строки, одна записывает JSON, другая - CSV.

## DI

Ручной DI-контейнер в [cmd/pos/container.go](cmd/pos/container.go) создаёт репозитории, экспортёры, прикладной сервис и консоль, передавая зависимости через конструкторы.

Объекты создаются при первом обращении и сохраняются в контейнере: один запуск использует одно хранилище. Ошибки конструкторов передаются дальше; неудачный результат не сохраняется.

## Как проверялось приложение

Основные команды из корня проекта:

```bash
go test ./...
go build ./...
```

Тесты проверяют ограничения модели, расчёт с разными весами и пропущенными оценками, исправление и отмену оценок, запрет изменения используемого критерия, работу репозиториев и экспортёров.
